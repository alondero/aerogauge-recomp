# Architecture

This project is a native PC program built around a translated N64 program.
The translated program is still the source of most game behavior. The
hand-written port supplies the pieces that the current runtime or renderer
does not provide.

## Main data flow

~~~text
USA ROM
  |
  |  symbol map, TOML, patches
  v
N64Recomp and RSPRecomp
  |
  v
RecompiledFuncs/ and src/aspMain.cpp       (generated, ignored)
  |
  +--------------------+
  |                    |
  v                    v
hand-written port   librecomp and ultramodern
  |                    |
  +----------+---------+
             v
       aerogauge_modern
             |
       SDL input/window/audio
             |
       RT64 display-list renderer
~~~

The ROM is needed for both the generated functions and the runtime ROM
reader. A release user does not run the recompiler. A source developer does.

## Guest and host boundary

| Area | Guest side | Host side | Owner |
| --- | --- | --- | --- |
| Game code | Recompiled N64 instructions and original data addresses | Generated C/C++ functions | N64Recomp plus ROM evidence |
| Main memory | Low 8 MiB of guest RDRAM | Host byte buffer | Runtime; hooks may read it through MEM helpers |
| OS services | libultra calls in the translated code | ultramodern and librecomp implementations | Runtime submodule |
| Window and input | N64 controller records | SDL window, keyboard, and gamepad snapshot | src/main.cpp |
| Graphics | N64 VI registers and display lists | RT64 swapchain and graphics API | RT64 plus src/rt64_renderer.cpp |
| Audio | RSP audio tasks and AI buffers | RSPRecomp output, SDL audio queue | src/aspMain.cpp and src/aero_audio.cpp |
| Saves | EEPROM and Controller Pak requests | Files in the application save directory | librecomp and src/aero_pak.cpp |

Guest code must not assume that a host pointer is a stable N64 pointer. Host
code must not read guest values with ordinary PC byte-order rules. Use the
N64Recomp memory helpers for guest words, halfwords, and bytes.

## Threads and ownership

The exact runtime thread implementation belongs to N64ModernRuntime. The
important ownership rules for this repository are:

| Thread or callback | Owns or does | Must not do |
| --- | --- | --- |
| SDL main thread | Pumps SDL events, samples the keyboard and first gamepad, applies window changes, and sends rumble commands | Call SDL from an arbitrary game thread; copy a save-state |
| Game thread(s) | Run generated game functions and port hooks at their documented game boundaries | Treat native thread contexts as guest memory that can be restored |
| VI callback | Observes VI timing, framebuffer swaps, scene changes, and test limits | Become a second graphics owner |
| Graphics thread | Receives a graphics task and sends its display list to RT64 or the headless renderer | Mutate game logic to make a capture look right |
| Audio path | Runs the generated audio microcode and queues PCM | Assume a missing host audio device means the game has no audio work |
| Save worker | Publishes EEPROM file updates through the runtime | Be used as a general-purpose port-state store |
| RT64 internal threads | Interpret display lists and present frames | Be given SDL window ownership |

The SDL main thread publishes input as one atomic snapshot. The game thread
reads that snapshot through the runtime input callback. This keeps SDL calls
off the game thread.

The game updates at its native cadence. The VI timing callback runs more
often than the 30 fps gameplay update in the current ROM. RT64 may present
interpolated frames between game updates. An interpolated frame is a renderer
feature; it is not an extra game update.

## Generated code

The normal translation boundary is:

| Input | Output | How it changes |
| --- | --- | --- |
| ROM and scripts/gen_syms_toml.py | aerogauge.syms.toml | Generated symbol table; review the diff and do not edit the output |
| ROM and scripts/gen_syms_toml.py | aerogauge.us.toml | Generated hooks and stubs; review the diff and do not edit the output |
| RSP symbol and microcode evidence | aspMain.us.toml | Hand-maintained RSPRecomp input |
| ROM and aerogauge.us.toml | RecompiledFuncs/ | Regenerated by N64Recomp |
| ROM and aspMain.us.toml | src/aspMain.cpp | Regenerated by RSPRecomp |
| force_stub.txt and scripts/gen_syms_toml.py | Stubs in aerogauge.us.toml | Hand-maintained list; regenerate the output |

The generated directory is a build product. Do not fix generated C by hand.
Change its input, regenerate it, and review the generated diff only as
evidence of the input change.

The current symbol generator uses discovered calls and IDO-style stack
prologues to propose function boundaries. That is a bootstrap method. A
plausible name or boundary is not proof. Use the
[reverse-engineering issue template](../.github/ISSUE_TEMPLATE/reverse_engineering.md)
for an uncertain boundary, then put the confirmed rule in the source, test, or
ROM reference.

## Hooks and patches

The game TOML marks some functions as stubs or ignored and inserts narrow
hooks at ROM-derived instruction addresses. The hand-written implementation
then runs with the live guest-memory buffer and recompiled context.

Dependency patches are separate. The current build applies these patches to
pinned public submodules:

| Dependency | Local changes |
| --- | --- |
| N64ModernRuntime | Scheduler and VI behavior, save-state thread-context relink, PI completion messages, synchronous non-graphics RSP handling, EEPROM flush on exit |
| RT64 | Angular-velocity-aware matching, sky backdrop handling, split-screen wide viewport handling, view/projection decomposition pivot, overscan aspect detection |
| RT64's Plume submodule | MinGW Direct3D 12 ABI compatibility |

The full list and patch order are in the
[patch inventory](../patches/README.md) and [BUILDING](../BUILDING.md). Patch
contents are part of the build contract. A dependency change is not complete
until the patch, build scripts, tests, and stable reference agree.

## Current port-side replacements

The most important native pieces are:

- aero_config owns persistent JSON settings and the main-thread snapshot.
- aero_menu owns the RecompFrontend settings overlay and its main-thread
  action queue. The same code is built on the Windows and Linux paths.
- aero_audio connects generated aspMain output to SDL audio. Headless runs use
  a virtual audio FIFO for game backpressure.
- aero_pak provides one raw 32 KiB Controller Pak image for Controller 1.
- aero_hud_widescreen rewrites selected display-list commands and one matrix
  for the widescreen HUD.
- aero_full_track registers course geometry beyond the original three-zone
  visibility window.
- aero_savestate copies the low 8 MiB guest-memory image at a settled frame
  boundary for debugging.
- aero_warp and aero_turbo_boost provide developer/test input paths.

These are not all equally mature. The configuration and audio paths are used
by the current release. Full-course rendering, save-state loading, and the
widescreen display-list rewrites still have broader validation work.

## Guest-memory writes are transitional

Several port features write directly into guest memory:

1. full-track mode builds synthetic display lists in an unused high RDRAM
   region and links them into game-owned node lists;
2. the HUD pass re-emits commands and changes a matrix through the game's
   display-list cursor; and
3. save-state loading copies a snapshot over the low 8 MiB and repairs a
   small set of native thread-context references.

This works only because the current ROM layout, allocator use, byte order,
thread timing, and display-list shape were measured together. It is fragile.
An address, buffer size, pointer lifetime, or background task can change the
result. These writes are transitional infrastructure, not a design target.

The intended path is:

~~~text
ROM evidence
    -> stable names and symbols
    -> decompiled/source-level game code
    -> explicit source patch or named code-mod seam
    -> versioned mod and asset interfaces
~~~

Until that path is available, a new hook must document:

- the exact ROM evidence;
- which thread calls it;
- which guest addresses it reads or writes;
- the byte-order and bounds assumptions;
- how it fails closed;
- a regression test or capture; and
- the decision that will allow the hook to be removed.

Do not add a general-purpose guest-memory API just to make a new feature
convenient. Ask whether the behavior belongs in decompiled game code, a
runtime service, RT64, or a future mod interface.

## Renderer boundary

RT64 owns display-list interpretation, native presentation, resolution,
aspect-ratio handling, interpolation, extended GBI commands, and texture
replacement. The port owns the wiring from ultramodern, the SDL window
handle, the game's ROM-specific display lists, and the settings snapshot.

The custom RT64 changes and their upstream status are recorded in
[the renderer reference](reference/renderer.md). The short rule is:

- a game-specific display-list workaround belongs in the port or ROM patch;
- a general renderer bug needs an isolated test and an upstream proposal; and
- a host compiler compatibility fix must stay small and be removed when the
  pinned upstream supports the same compiler.

The headless software renderer in stub_renderer.cpp is a test and capture
instrument. It is not the long-term player renderer.

## Audio and saves

The current audio path is:

~~~text
generated game audio task
    -> generated aspMain RSP code
    -> AI buffer callback
    -> byte-order correction and SDL queue
~~~

The current save path is:

~~~text
game EEPROM or Controller Pak call
    -> librecomp save service or aero_pak native hook
    -> per-user save file
~~~

The save-state feature is different from game saves. It is a developer
snapshot of guest memory. Native stacks, native registers, and background
work are not serialized. Only use it at a settled frame, and treat a
windowed load during live rendering as unsafe until the open issue is fixed.

## Failure and shutdown model

The headless smoke path may end the process with _Exit after flushing EEPROM.
This avoids tearing down runtime memory while generated game threads still
exist. It is suitable for a bounded test, not proof that normal game-thread
shutdown is solved. The window close path uses the same current process-exit
model. A future graceful-shutdown change needs an explicit runtime decision and
thread join test.
