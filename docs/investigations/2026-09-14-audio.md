# Audio buffering investigation — 2026-09-14

This record keeps the durable audio findings that were previously embedded in
source comments. It is historical evidence, not a new pass/fail result. The
observations below came from existing comments, tests, generated-code inputs,
and build files. This audit did not rerun the ROM-backed audio checks.

## Observed failure chain

- The translated game submits audio work through M_AUDTASK. Generated aspMain
  mixes the task and sends PCM to the host callback.
- The audio length comes from an N64 AI register with a 256 KiB maximum DMA
  size. A garbage-sized early submission was observed in the original
  investigation. The queue rejects an over-size request before reading its
  payload; test_audio_oversize_guard protects that boundary.
- The host converter must retain resampler state between submissions. A
  converter created for each small buffer reset its filter state at every
  boundary and produced audible corruption when the source and device rates
  differed. The current code uses one persistent SDL stream per source rate.
- A headless run has no device that drains SDL audio. The virtual AI FIFO
  therefore models the guest-side drain rate so the mixer does not see a
  permanent empty queue. It is a test aid, not a claim that a headless run
  produced speaker output.

## Current boundary

The generated game and RSP code own the guest task and source buffers. The
audio module owns byte-order correction, host conversion, SDL queueing, and
the headless FIFO. SDL owns the host device. These layers have different
failure signals, so a diagnosis should capture the first boundary that fails.

The content probe runs before the host-device check. A non-silent PCM message
therefore proves that the generated path submitted non-zero samples, but not
that a device played them. A device log, queue statistics, and a real-device
test are still needed for playback claims.

## Falsifying checks

Use one ROM identity, port commit, host, audio driver, and generated-code
inputs when repeating the work. The relevant checks are:

- audio_playback_buffering for queue and conversion behavior;
- audio_intro_playback on Windows with a real audio device;
- audio_task_crash for the headless generated task path; and
- AERO_AUDIO_RMS=1 and AERO_AUDIO_STATS=1 for boundary logs.

If these checks disagree, record the smallest failing boundary before changing
the FIFO or the generated audio path. The long-term owner of the guest audio
contract is still an open architecture question; this documentation pass does
not change it.
